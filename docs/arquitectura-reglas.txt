## Contexto general del proyecto

SAHUR es una aplicación Full Stack desarrollada con:

- Frontend: Angular
- Backend: ASP.NET Core / .NET
- Lenguaje frontend: TypeScript
- Lenguaje backend: C#
- Comunicación: REST API mediante HTTP/JSON
- API externa: Fake Store API
- Persistencia simulada: Entity Framework Core InMemory
- Control de versiones: Git + GitHub
- IDE principal: VS Code

El proyecto está separado en:

```text

│
├── frontend/
│   └── sahur-web/
│
├── backend/

```

## REGLA PRINCIPAL

Este proyecto debe cumplir de manera ESTRICTA con:

- MVVM
- SOLID
- CQRS
- Dependency Injection
- Separación de responsabilidades
- Arquitectura por capas

```text

↓

↓

↓

↓

↓

↓

```

## View

La View corresponde principalmente a:

- archivos HTML;
- componentes visuales;
- bindings;
- eventos;
- presentación de información.

La View NO debe contener lógica de negocio.

El componente TypeScript asociado a una View debe mantenerse lo más sencillo posible.

Idealmente debe limitarse a trabajar con su ViewModel.

Ejemplo conceptual:

```typescript
export class CatalogComponent {
  readonly vm = inject(CatalogViewModel);
}
```


# BACKEND - .NET

El backend utiliza **CQRS estricto**.

Todas las operaciones deben clasificarse como:

```text
COMMAND
```

o:

```text
QUERY
```

Nunca deben mezclarse.

## Queries

Una Query:

- consulta información;
- NO modifica estado;
- tiene su propio QueryHandler.

Ejemplos:

```text
GetProductsQuery
GetProductByIdQuery
GetUsersQuery
GetAuditRecordsQuery
```

Cada Query debe tener su Handler correspondiente.

Ejemplo:

```text
GetProductsQuery
GetProductsQueryHandler
```

## Commands

Un Command:

- crea;
- modifica;
- elimina;
- cambia el estado del sistema.

Ejemplos:

```text
CreateProductCommand
UpdateProductCommand
DeleteProductCommand
AddProductToCartCommand
CreateAuditCommand
```

Cada Command debe tener su Handler.

Ejemplo:

```text
CreateProductCommand
CreateProductCommandHandler
```

# CQRS Y REPOSITORIOS

Siempre que sea posible, separar lectura y escritura.

Ejemplo:

```text
IProductReadRepository
IProductWriteRepository
```

No quiero una interfaz gigante como:

```text
IRepository
```

con todas las operaciones del sistema.

Esto también ayuda a cumplir Interface Segregation de SOLID.

---

# SOLID

Todas las implementaciones deben respetar estrictamente los cinco principios.

## S - Single Responsibility Principle

Cada clase debe tener una única responsabilidad.

No crear servicios gigantes.

## O - Open/Closed Principle

La aplicación debe poder extenderse mediante nuevas implementaciones sin modificar innecesariamente las clases existentes.

Usar abstracciones cuando corresponda.

## L - Liskov Substitution Principle

Las implementaciones deben respetar los contratos de sus interfaces.

Una implementación debe poder sustituir a otra sin romper al consumidor.

## I - Interface Segregation Principle

Preferir interfaces pequeñas y específicas.

Ejemplo correcto:

```text
IProductReadRepository
IProductWriteRepository
```

en lugar de una interfaz genérica con muchas responsabilidades.

## D - Dependency Inversion Principle

Las capas superiores deben depender de abstracciones, no de implementaciones concretas.

Utilizar Dependency Injection.

Evitar:

```text
new Repository()
new HttpClient()
new DbContext()
```

dentro de clases de negocio.

# BASE DE DATOS SIMULADA

Se utiliza Entity Framework Core InMemory.

Debe tratarse como una persistencia real mediante:

```text
DbContext
DbSet
Repositories
SaveChangesAsync
```

No quiero listas globales improvisadas dentro de Controllers.

La ventaja es que posteriormente pueda reemplazarse InMemory por SQL Server, MySQL, PostgreSQL u otro proveedor sin modificar las capas superiores.
