VIEW
==================================================

La View corresponde principalmente a:

- archivos HTML;
- templates;

- bindings;
- eventos de interfaz;
- presentación de información.

La View NO debe contener lógica de negocio.

La View NO debe:

- consumir HttpClient;
- consumir endpoints directamente;
- usar repositorios directamente;
- consultar la base de datos;
- contener reglas de negocio;
- decidir procesos complejos;
- conocer detalles del backend;
- realizar transformaciones de dominio importantes.

El TypeScript asociado a una View debe mantenerse lo más pequeño posible.

Idealmente debe limitarse a:

- recibir eventos;
- leer parámetros visuales;
- delegar operaciones al ViewModel;
- mostrar estado.

Ejemplo conceptual:

}

La View habla con el ViewModel.

NO con Repository.
NO con HttpClient.
NO con Backend directamente.

==================================================

- consulta estado;
- NO modifica datos;

==================================================
SOLID
==================================================

Todas las implementaciones deben respetar estrictamente los cinco principios.

==================================================
S - SINGLE RESPONSIBILITY PRINCIPLE
==================================================

Cada clase debe tener una responsabilidad claramente definida.

Ejemplos:

ProductReadRepository:
lectura de productos.

ProductWriteRepository:
escritura de productos.

GetProductsQueryHandler:
resolver GetProductsQuery.

CatalogViewModel:
estado del catálogo.

NO crear clases gigantes como:

ProductService
SystemManager
ApplicationService
GeneralRepository

que hagan múltiples cosas sin relación.

==================================================
O - OPEN/CLOSED PRINCIPLE
==================================================

El código debe poder extenderse sin modificar innecesariamente consumidores existentes.

Depender de abstracciones cuando sea apropiado.

Ejemplo:

IProductReadRepository

puede tener:

EfProductReadRepository

y en el futuro:

SqlProductReadRepository

sin modificar el Handler que depende de la interfaz.

==================================================
L - LISKOV SUBSTITUTION PRINCIPLE
==================================================

Las implementaciones deben respetar sus contratos.

Una implementación concreta debe poder sustituir a otra sin cambiar el comportamiento esperado del consumidor.

No crear implementaciones que rompan semánticamente una interfaz.

==================================================
I - INTERFACE SEGREGATION PRINCIPLE
==================================================

Preferir interfaces pequeñas y específicas.

Correcto:

IProductReadRepository
IProductWriteRepository

Incorrecto:

IProductRepositoryWithEverything

cuando un consumidor únicamente necesita lectura.

==================================================
D - DEPENDENCY INVERSION PRINCIPLE
==================================================

Las capas superiores dependen de abstracciones.

No de implementaciones.

Usar Dependency Injection.

Evitar dentro de lógica de aplicación:

new Repository()
new DbContext()
new HttpClient()
new Handler()

Las dependencias deben ser suministradas por el contenedor de DI.

==================================================
DEPENDENCY INJECTION
==================================================

Toda implementación debe registrarse explícitamente en la capa adecuada.

Ejemplo conceptual:

services.AddScoped<IProductReadRepository, ProductReadRepository>();

Nunca ocultar dependencias mediante:

new
Service Locator
variables globales
singletons improvisados

A menos que exista una justificación técnica válida.
